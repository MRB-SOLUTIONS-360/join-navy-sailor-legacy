# Deep Dive — Admin Simple CRUD Entities

Scope: `CanDesignationController`, `DistrictsController`, `EligibilityController`, `SailorBatchConfigurationController`, `SailorBatchsController`, `SailorCentDistMappingController`, `SailorCentersController`, `SubjectsController`, `UnionsController`, `UpozilasController` (all under `backend/controllers/`) — every backend "reference data" CRUD controller in this repo except `SailorsController`/`DeSailorsController`/`UserController` (large, candidate-facing/user-management controllers covered elsewhere).

Method note vs. the officer-portal reference doc: this is a stock **Yii2 2.0 advanced-template** app, not Laravel/Blade. There's no route file to grep — each controller's `actionIndex/actionView/actionCreate/actionUpdate/actionDelete` **is** the route (Yii2's default `[controller]/[action]` URL rule), and each CRUD form is a single `_form.php` partial shared by both `actionCreate()` and `actionUpdate()` rather than separate Blade `create`/`edit` views. Evidence below is file:line from `backend/controllers/*.php`, `common/models/*.php`, `backend/views/*/{index,_form}.php`, cross-referenced against `docs/00-inventories/{controller_inventory,model_inventory,middleware_inventory,component_inventory}.md`.

## Shared convention (stated once, not repeated per entity)

All 10 controllers are standard **Gii-scaffolded** CRUD controllers with the exact same shape:

- **`behaviors()`**: `array_merge(parent::behaviors(), ['verbs' => ['class' => VerbFilter::class, 'actions' => ['delete' => ['POST']]]])` — i.e. only `actionDelete` is verb-restricted to POST; every other action accepts GET. 8 of the 10 define **no** `AccessControl` at all. `UnionsController` and `UpozilasController` are the two outliers that do (detailed in their own sections below).
- **App-level auth gate**: none of these controllers need their own login check because `backend/config/main.php`'s app-level `'as access' => ['class' => AccessControl::class, 'rules' => [..., ['allow' => true, 'roles' => ['@']]]]` behavior fires on **every** backend controller/action via the `EVENT_BEFORE_ACTION` bubbling described in `middleware_inventory.md:7-9,45-58` — any authenticated user (`roles => ['@']`), regardless of role/permission, can reach every action documented below. There is no spatie/permission-style per-entity gate anywhere in this scope, matching the officer-portal's finding.
- **`actionIndex()`**: `new {Entity}Search(); $searchModel->search($this->request->queryParams); return $this->render('index', [...])` — GET-only filter form + `ActiveDataProvider`, real server-side filtering/sorting/pagination (not a dead DataTables shell — `component_inventory.md:135`).
- **`actionCreate()`**: `$model = new {Entity}(); if (isPost) { if ($model->load(post) && $model->save()) { flash('success', "..."); $model = new {Entity}(); } } else { $model->loadDefaultValues(); } return $this->render('_form', ['model' => $model]);`. Note the **re-render pattern**: unlike the Gii default (`redirect(['view', 'id' => $model->id])`), every controller in this scope re-renders a **blank** `_form` on success (the `view.php`/`actionView` stub exists but is never redirected to from Create/Update) — the admin sees a flash banner and an empty form again, not the record they just created. `actionView($id)` exists on every controller but is not linked from any `index.php`'s `ActionColumn` (`template` never includes `{view}` in any of the 10 index views read) — reachable only by typing the URL directly.
- **`actionUpdate($id)`**: same shape, re-renders `_form` populated with the (possibly just-saved) model on success rather than redirecting.
- **`actionDelete($id)`**: `$this->findModel($id)->delete(); return $this->redirect(['index']);` — a real, working `ActiveRecord::delete()` call in **all 10** controllers (unlike the officer-portal repo, where 11 of 13 `destroy()` methods are empty stubs). Whether it's *reachable from the UI* depends entirely on the `ActionColumn` `template` in that entity's `index.php` — see the per-entity table below.
- **`findModel($id)`**: `{Entity}::findOne(['id' => $id]) ?? throw NotFoundHttpException`.
- **Views**: `index.php`, `_form.php`, `view.php` per module (`create.php`/`update.php` do **not** exist for any of these 10 — confirmed via directory listing — `_form.php` is rendered directly by the controller and branches on `$model->isNewRecord` for the page title/submit-button label, e.g. `can-designation/_form.php:13`: `$this->title = $model->isNewRecord ? 'Add Designation' : 'Update Designation ' . $model->name_en;`).
- **Layout**: every view extends the `admin` layout (`backend/config/main.php:17`), which registers `backend\assets\AppAdminAsset` — and unlike the frontend candidate portal (whose `AppNavyAsset` has `$depends` fully commented out), **`AppAdminAsset` does declare `yii\web\YiiAsset`** (`component_inventory.md:162`). That means `yii.js`/`yii.activeForm.js` are actually loaded on every page in this scope, so (a) client-side `ActiveForm` validation runs before submit, and (b) Yii2's `ActionColumn` `{delete}` link's built-in `data-confirm` JS dialog ("Are you sure you want to delete this item?") **actually fires** wherever a `{delete}` template exists — this is the opposite of the officer-portal's dead-JS Blade `.remove` links, so "delete is wired to a working confirm dialog" is the default assumption here, not the exception.
- **Flash messages**: hand-rolled inline in each `_form.php` (`<?php if (Yii::$app->session->hasFlash('success')): ?><div class="alert alert-success">...`) — the shared `common\widgets\Alert` widget is imported but never called from any layout actually assigned to these controllers (`component_inventory.md:27`), so this per-view inline block is the only place the flash text is ever rendered.
- **`beforeSave($insert)`**: present on every model in scope, stamping `created_by`/`created_dt` on insert or `updated_by`/`updated_dt` on update from `Yii::$app->user->identity->id` (fallback `1`/`2` if no identity) — identical boilerplate across all 10 models.
- **Status values**: shared `StaticMethod::statusDropDown()` = `[Constants::STATUS_ACTIVE => 'Active', Constants::STATUS_INACTIVE => 'Inactive']` (`common/static/StaticMethod.php:15-19`, `Constants::STATUS_ACTIVE = 1` / `STATUS_INACTIVE = 2`, `common/static/Constants.php:8-9`), reused as the `status` field's datasource across all 10 entities.
- **Datepicker**: where a date field exists (`SailorBatchs`, `SailorBatchConfiguration`), the form pulls **Flatpickr from a CDN `<link>`/`<script>` tag inlined directly in `_form.php`** (`sailor-batchs/_form.php:16-17`, `sailor-batch-configuration/_form.php:32-34`) rather than `yii\jui\DatePicker` (the pattern used elsewhere in the app per `component_inventory.md:126-130`) — these two forms are the only CDN-script-tag exception in the whole `backend/views/` tree.
- **No modals** exist in any of these 10 modules — all CRUD is full-page `_form.php`, matching the officer-portal's finding for its own simple-CRUD scope.

## Eligibility — multi-select explode/implode detail

`EligibilitySetting`'s equivalent in this repo is the much smaller `Eligibility` model, but it still uses the same comma-string-column pattern for its 6 multi-value fields.

- **`Eligibility::implodeFieldList()`** (`Eligibility.php:185-188`) returns exactly 6 attribute names: `marital_status, gender, ssc_ac_group, hsc_ac_group, hons_diploma_subject, trade_course_subject`.
- **On save** (`beforeSave()`, `Eligibility.php:158-179`): for every field in that list, if the current value on the model `is_array()`, it's `implode(',', ...)`'d into the attribute before `parent::beforeSave()` runs — this fires for **both** create and update, unconditionally, on any array-typed attribute the form submitted (checkbox groups and Select2 multis both post as PHP arrays).
- **On update-GET (populating the form for editing)** — `EligibilityController::actionUpdate()` (`EligibilityController.php:102-106`):
  ```php
  foreach ($model::implodeFieldList()  as $key => $value) {
      if ($model->$value)
          $model->$value = explode(',', $model->$value);
  }
  ```
  runs **after** the `if ($this->request->isPost && ...)` block, on every GET *and* every POST request that reaches the render — so the CSV column is re-exploded into an array right before `_form.php` renders it back into `checkboxList()`/Select2 `'value' => $model->field`. **Note the asymmetry with `actionCreate()`**, which has no equivalent explode step at all (a blank `new Eligibility()` has no CSV value to explode in the first place, so this isn't a bug, just an asymmetry worth naming — Create never needs it, Update always does).
- **`candidate_designation` dropdown is populated only conditionally**: `_form.php:57-62` — `$can_desi = []; if (!$model->isNewRecord) $can_desi = CanDesignation::getAllActiveDesignation(type: $model->candidate_type);` — on **Create**, the dropdown starts genuinely empty (no options at all beyond the `'prompt'`) until the page's inline AJAX handler fires.
- **The one client-side AJAX interaction in this scope lives here**: `eligibility/_form.php:215-250` — a `change` handler on `#eligibility-candidate_type` hits `GET /ajax/get-candesignation-by-cantype?candidate_type=X` and repopulates `#eligibility-candidate_designation`'s `<option>` list from the JSON response. This is the sailor-app's direct analogue of the officer-portal's district→upozila cascade, just for candidate-type→designation instead of geography, and — unlike Unions above — it *is* wired up here.
- **Compound uniqueness**: `['candidate_designation', 'unique', 'targetAttribute' => ['candidate_designation', 'candidate_type']]` (`Eligibility.php:66`) means the same designation can have separate eligibility rows under different candidate types, but not two rows for the same (designation, type) pair — enforced at save time, not surfaced as a client-side check anywhere in the form.

## Sailor Batch Configuration — nested exam-date sub-resource detail

This is the most structurally complex form in scope: a single `SailorBatchConfiguration` parent record owns a **variable-length list of `SailorBatchConfigurationExamDate` child rows**, managed inline in the same page/POST rather than as a separate CRUD screen.

### Data shape
- `SailorBatchConfigurationExamDate` (`common/models/SailorBatchConfigurationExamDate.php`) — `batch_configuration_id` (required, FK), `exam_date`, `max_candidate_this_date`, `status` (defaults to `1`/Active).
- Relation: `SailorBatchConfiguration::getExamDates()` → `hasMany(SailorBatchConfigurationExamDate::class, ['batch_configuration_id' => 'id'])` (`SailorBatchConfiguration.php:179-182`).
- The parent model **also** carries a legacy scalar `exam_date` column of its own (`@property string|null $exam_date`, doc comment `SailorBatchConfiguration.php:20`) which the controller keeps in sync with just the **first** child row's date (`$model->exam_date = $post['exam_date'][0] ?? ''` — `SailorBatchConfigurationController.php:85`, `124`) — i.e. the parent's single `exam_date` field is a denormalized copy of `examDates[0]`, used wherever the rest of the app reads `SailorBatchConfiguration::exam_date` directly instead of joining the child table (e.g. the `index.php` grid column, `sailor-batch-configuration/index.php:157`, prints the raw parent `exam_date` value, not an aggregate of all child dates).

### Create/Update flow
- **`actionCreate()`** (`SailorBatchConfigurationController.php:73-103`): after `$model->save()` succeeds, calls `$this->batchConfigurationExamDate($post, $model->id)` to persist the child rows, then **discards** the just-created `$model` and re-renders a **blank** form with `$examDates = [new SailorBatchConfigurationExamDate()]` (a single empty row) — same "re-render blank form on success" pattern as every other entity in this scope, just extended to the child collection too.
- **`actionUpdate($id)`** (`SailorBatchConfigurationController.php:112-145`): same flow, but on success re-fetches the model and does `$examDates = $model->examDates ?: [new SailorBatchConfigurationExamDate()]` — i.e. loads the real child rows back from the DB relation for display.
- **`batchConfigurationExamDate()`** (protected helper, `SailorBatchConfigurationController.php:148-167`): iterates the posted `exam_date[]`/`max_candidate_this_date[]`/`id[]` parallel arrays by index. For each index: if `exam_date[$key]` is non-empty, **upsert** (`SailorBatchConfigurationExamDate::findOne($ids[$key]) ?: new SailorBatchConfigurationExamDate()`, then set fields and `save()`); if the date is empty **and** an `id` was posted for that slot, the row is `delete()`'d outright. There is no transaction wrapping the parent `save()` + this child-row loop — a failure partway through the loop leaves the parent saved but the child set only partially updated.
- **AJAX validation branch**: both `actionCreate()` and `actionUpdate()` open with `if (Yii::$app->request->isAjax && $model->load(post)) { return ActiveForm::validate($model); }` (`SailorBatchConfigurationController.php:77-80`, `116-119`) — standard Yii2 client-side `ActiveForm` AJAX validation, consistent with `enableAjaxValidation => true` set on the form (`_form.php:50`) and on several individual fields (`group_start_roll`, `group_end_roll`, `group_no_of_candidate`, the 5 `*_can_total` fields, and the exam-date `exam_date[]` field itself — `_form.php:135`, `188-217`).

### Client-side UI for the exam-date rows (`sailor-batch-configuration/_form.php:115-352`)
- Rows render 3-per-`<div class="row">` (`$index % 3 == 0` starts a new row wrapper), each with a Flatpickr-bound date `<input>` (`.dp`, readonly, `Y-m-d`) and a `max_candidate_this_date` number input, plus a hidden `SailorBatchConfigurationExamDate[id][]` carrying the existing row's PK (or blank for a brand-new row).
- **"Add More Exam Dates" button** (`#add-exam-date-row`) — pure client-side jQuery template-string append, no AJAX; it re-implements the same 3-per-row layout and Flatpickr re-init logic in JS, duplicating the PHP-rendered markup shape by hand (two independent implementations of "render one exam-date row" that must be kept visually in sync).
- **Per-row delete (`&times;` span, `onclick="deleteExamDate(this)"`)**: only rendered for `$index > 0` (`_form.php:156`) — the **first** exam-date row can never be removed via this control, matching the parent's denormalized-`exam_date`-from-index-0 design (there must always be at least one row). Deletion is a **real AJAX call** — `fetch()` with method `DELETE` to `sailor-batch-configuration/delete-exam-date` (routes to `SailorBatchConfigurationController::actionDeleteExamDate()`, `SailorBatchConfigurationController.php:188-211`), which decodes the raw JSON request body, finds and deletes the `SailorBatchConfigurationExamDate` by id, and returns a JSON `{success, message}`. A native `confirm()` dialog gates the request client-side (`_form.php:241-243`) — this is the one delete-confirmation UI in the whole scope that is **hand-rolled JS**, not the Yii2 `ActionColumn` `data-confirm` mechanism used everywhere else.
- **District Select2 is dependent on Center** (a second cascading-dropdown instance in this scope, alongside Eligibility's candidate-type→designation one): `change` handler on `#sailorbatchconfiguration-center_id` (`_form.php:354-400`) hits `GET /ajax/get-all-assigned-district-by-center?center=X` and repopulates the `district_slug` Select2 from `SailorCentDistMapping::GetAllAssignedDistrictByCenter($center_id)` — i.e. the district multi-select is scoped to whichever districts have been mapped to the selected center via the separate Sailor Center-District Mapping entity above, not a flat list of all districts.
- **`validateOnRollSwap` server-side conditional-required** (see model table row above) has **no client-side mirror** — `group_start_roll`/`group_end_roll` are always rendered as plain optional-looking text inputs regardless of the `roll_swap_in_group` radio's current value; the "actually required if Swap Roll = Yes" rule only surfaces as a server round-trip validation error, not a live show/hide or asterisk toggle.

## Access-control outliers — Unions & Upozilas

Per the task brief and confirmed in `middleware_inventory.md:170-180, 346-364`, `UnionsController` and `UpozilasController` are the **only two controllers in this entire deep-dive scope** (and, per `controller_inventory.md:538`, one of only 5 controllers across the *whole backend app*) that declare their own `AccessControl` behavior:

```php
'access' => [
    'class' => \yii\filters\AccessControl::className(),
    'rules' => [
        [
            'allow' => true,
            // 'actions' => ['delete'],  // Specify the actions you want to restrict
            'roles' => ['@'],  // Only authenticated users (@) can access this action
        ],
        [
            'allow' => false,  // Deny access to other users
            // 'actions' => ['delete'],
        ],
    ],
],
```
(`UnionsController.php:25-38`, `UpozilasController.php:25-38` — byte-for-byte identical block, including the two commented-out `'actions' => ['delete']` lines in both files, suggesting a copy-paste from a shared scratch snippet that was never finished).

**This is functionally inert.** Because `backend/config/main.php`'s app-level `'as access'` behavior already gates every backend action to `roles => ['@']` (§ Shared convention above), this controller-level block re-checks the exact same condition a second time. The commented-out `'actions' => ['delete']` restriction that would have made this block *do* something different (e.g. requiring a stronger role just to delete) was never turned on — both `allow => true` and the fallback `allow => false` apply to **all** actions (no `'actions'` key present in either rule), so the net behavior is identical with or without this block. The other 8 controllers in scope get the same effective protection for free from the app-level filter; Unions and Upozilas simply duplicate it. `middleware_inventory.md:351` labels this exact pattern "None — just duplicated."

There is no other functional difference between Unions/Upozilas and the other 8 entities in this scope — their CRUD shape, delete-unreachable-from-index-UI status (see table above), and model conventions are otherwise identical to Districts (their closest sibling, also geo-hierarchy data with an unreachable-but-working delete route).
