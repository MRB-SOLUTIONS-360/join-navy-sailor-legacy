## 1. Current architecture summary

### Two physically separate Yii2 applications, not one app split by a column

This is the single biggest structural fact about this codebase, and the biggest difference from the sibling Laravel app. `join-navy-sailor-legacy` is a stock **Yii 2.0 "advanced" project template**: `common/`, `frontend/`, `backend/`, and `console/` are four independently-bootstrapped tiers sharing one codebase, not four route groups inside one application (`01-architecture/architecture_document.md` §2, §19; `01-architecture/portal_map.md` "Foundational fact"). `frontend/` and `backend/` are each their **own `yii\web\Application` instance** — own entry script (`frontend/web/index.php` / `backend/web/index.php`), own `webroot`, own `config/main.php`, own session cookie name (`join_bd_navy_front` vs `join_navy-backend`), own identity cookie name (`_join_bd_navy_front` vs `_join_navy-backend`) (`01-architecture/portal_map.md` table; `00-inventories/middleware_inventory.md` §2). "Admin" is not a URL prefix here the way `Route::prefix('admin')` is in the officer-app — it is a wholly separate application, reached at its own webroot/subdomain per deployment. Both apps do share one underlying table: `common\models\User` (`{{%user}}`), so an admin row and a candidate row live side by side in the same table — but a candidate authenticated on `frontend` carries no session into `backend`, and vice versa; cookie-namespace isolation is the practical tier boundary, not a shared guard layer.

### No Services/Repository layer — fat controllers and fat ActiveRecord models

Yii2 has no `app/Services`-equivalent in this codebase at all (`01-architecture/architecture_document.md` §4). Business logic lives in two places:

- **Fat controllers.** `backend/controllers/ReportController.php` is 1,605 lines / 76.6 KB with 23 actions — the largest single PHP file in the repo — and has no delegated service class (`00-inventories/controller_inventory.md` "ReportController" section). `frontend/controllers/SailorCandidateController.php` (1,195 lines) and `frontend/controllers/DeSailorController.php` (1,118 lines) each inline the full multi-step application-wizard logic — photo upload, PII encryption, roll-number/exam-date allocation, PDF generation — directly in `action*()` methods (`00-inventories/repository_inventory.md`; `04-deep-dives/deepdive_frontend_application_wizard.md` §0, §7).
- **Fat ActiveRecord models.** `common/models/Sailors.php` (1,315 lines, the largest model in the app) and its near-twin `common/models/DeSailors.php` each carry ~15-18 custom inline validators encoding Bangladesh-Navy-specific eligibility/academic-track business rules directly inside `rules()`, plus static helper methods (`numberOfApplication()`, `nextRollByBatchId()`, `getLastRollExamDateByDesignationCenter()`, `generateLog()`) that controllers call directly — there is no service abstraction between them (`00-inventories/model_inventory.md` §16, "Sailors vs. DeSailors").

The closest things to a Services layer are `common/components/R2Storage.php` (a real Yii application component, `Yii::$app->r2Storage`, combining Cloudflare R2 file storage and NDJSON audit-log read/write in one class), `common/models/payment/SSLPayment.php` (a static-method payment class living under `models/` by path convention only, not an ActiveRecord), and `common/static/{StaticMethod,AES256CTR,DataEncryption,SendSms,Constants}.php` (plain static helper classes — the de facto services layer for encryption/SMS/misc constants) (`01-architecture/architecture_document.md` §4; `00-inventories/service_inventory.md`). None of these are DI-registered in the Laravel sense; `R2Storage` is the only one that is even a registered Yii component, and it's reached via `Yii::$app->` service-locator, not constructor injection. There is also no `app/Jobs`-equivalent: zero `yii\queue` usage anywhere in the repo (`00-inventories/service_inventory.md` §5) — roll-number generation, PDF rendering, and audit logging all run synchronously inline inside the HTTP request that completes an application, not as a dispatched background job. This is the one place the sailor app has *strictly less* infrastructure than the officer app, which has a working `App\Jobs\ProcessRollGeneration` queued job.

### `User.user_type` checked once at login, sparse/inconsistent `AccessControl`

There is no RBAC package, no `authManager` component, and no per-request middleware-equivalent re-check anywhere in this codebase (`01-architecture/role_permission_matrix.md` §0). Authorization is built from three ingredients:

1. **Physical app separation** (above) — the actual load-bearing boundary.
2. **A single `User.user_type` string column** (`admin` / `candidate`), checked **exactly once, at login time**, inside `common\models\LoginForm::validatePassword()`:
   ```php
   if ($user && $user->user_type != $this->user_type) {
       $this->addError($attribute, 'You are not ' . $this->user_type . ' user!');
   }
   ```
   The calling controller sets `$model->user_type` before validating — `'admin'` in `backend/controllers/SiteController.php:203`, `'candidate'` in `frontend/controllers/CandidateController.php:177` (`01-architecture/role_permission_matrix.md` §1a). There is **no per-request re-validation** analogous to the officer app's `IsAdmin`/`IsCandidate` middleware — Yii2 has no route-level middleware pipeline in which to place such a check in the first place. `user_type` itself is not even an enum or constant list anywhere; it's validated only as `[['user_group', 'user_type'], 'string']` in `common/models/User::rules()`.
3. **`yii\filters\AccessControl`, used sparingly.** Only **5 of 31 controllers** define any `AccessControl` at all: `frontend/SiteController` (dead scaffold — see §3), `frontend/SailorCandidateController` (partial — 2 of 10 actions), `backend/SiteController`, `backend/UnionsController`, `backend/UpozilasController` (`00-inventories/middleware_inventory.md` "Summary table"; `01-architecture/role_permission_matrix.md` §4). Backend gets real, centralized protection from a single **app-level** `AccessControl` behavior wired at `backend/config/main.php:132-144` (`'as access'`), which fires on `EVENT_BEFORE_ACTION` for every backend controller/action before any per-controller filter runs — so every route except `site/login`/`site/error` requires an authenticated user regardless of what the controller itself declares. **But that filter only checks role `@` (any authenticated `common\models\User`), never `user_type == 'admin'` specifically** (`00-inventories/middleware_inventory.md` §1b, "Important gap"). In practice the separate session/cookie namespaces (above) prevent a frontend candidate session from ever reaching backend routes, but nothing at the filter layer itself enforces the admin/candidate distinction — it's a config-only boundary.

   **Frontend has no app-level access-control equivalent at all** (`00-inventories/middleware_inventory.md` §1c, confirmed by reading the full 77-line `frontend/config/main.php`). Coverage there is opt-in, per-action, and genuinely inconsistent even within one controller pair: `SailorCandidateController` gates 2 of its 10 actions (`payment`, `academic-info`) with `AccessControl`; the other 8 — including `personal-info`, `complete-application`, `download`, `refund-phone`, `cancel-application` — have **no filter and no manual `isGuest` guard**, dereferencing `Yii::$app->user->identity->...` directly (would fatal, not cleanly redirect, for a guest). Its DE-Sailor-track sibling, `DeSailorController`, has **zero `behaviors()` override and zero `isGuest` checks anywhere**, for all 8 of its actions — strictly worse coverage than `SailorCandidateController` (`00-inventories/middleware_inventory.md` §3.6, §3.8; `04-deep-dives/deepdive_frontend_application_wizard.md` §0).

**Controller-level `AccessControl` count, exact:** 5 of 31 total (`frontend/SiteController`, `frontend/SailorCandidateController` [partial, one dead rule], `backend/SiteController`, `backend/UnionsController`, `backend/UpozilasController`). Of the backend's 21 controllers, only 3 have any `AccessControl` of their own, and two of those three (`UnionsController`, `UpozilasController`) duplicate the already-live app-level filter exactly — "functionally inert," per `01-architecture/role_permission_matrix.md` §3.3 and `04-deep-dives/deepdive_admin_crud_entities.md` "Access-control outliers." `backend/controllers/UserController.php` — which manages admin accounts and password hashes — has **no `AccessControl` of its own at all**, relying entirely on the single app-level filter (`00-inventories/controller_inventory.md`, `UserController` row; `01-architecture/portal_map.md` "Notable gap").

### `Sailors` vs `DeSailors`: two application tracks, not two roles

The "Sailor" (general) and "DE-Sailor" (Direct Entry — Artificer/Dockyard trade recruitment) tracks are **two fully separate `ActiveRecord` models backed by two separate tables** (`{{%sailors}}` / `{{%de_sailors}}`), not a subtype or single-table-inheritance relationship — but they are structural twins otherwise, sharing the same `SailorsQuery` base, identically-named static helpers, and a paired backend `*Reference` AR class each (`00-inventories/model_inventory.md` "Sailors vs. DeSailors"). Which track a candidate lands on is decided by data (`sailor_or_de_sailor`, computed from the candidate's eligibility-check answers inside `frontend/controllers/CandidateController.php::haveCeci()`), never by identity or role — both tracks authenticate through the exact same `user_type='candidate'` gate (`01-architecture/role_permission_matrix.md` §5; `01-architecture/portal_map.md` "The Sailor vs De-Sailor split"). See §6 below for the asymmetries this split introduces that a rebuild needs to preserve or deliberately reconcile.

## 2. Schema reconstruction risk

**Only 1 of ~29 tables in this application has any migration history in the repo, and even that one has drifted.**

`console/migrations/` contains exactly two files:
```
m130524_201442_init.php  → createTable('{{%user}}', [id, username, auth_key, password_hash,
                              password_reset_token, email, status, created_at, updated_at])
m190124_110200_add_verification_token_column_to_user_table.php → addColumn('{{%user}}', 'verification_token', string())
```
(`00-inventories/repository_inventory.md`; `00-inventories/model_inventory.md` "Migration file reference"; `01-architecture/architecture_document.md` §6.)

`common/models/` implies roughly **29 distinct domain tables** — `sailors`, `de_sailors`, `sailor_batchs`, `sailor_batch_configuration(_exam_date)`, `sailor_centers`, `sailor_cent_dist_mapping`, `eligibility`, `can_designation`, `can_eligibility_check_info`, `districts`, `upozilas`, `unions`, `subjects`, `send_sms`, `session`, etc. **None of these ~28 other tables has any migration in this repo.** The production schema was almost certainly built and evolved via direct SQL/import, not through Yii's migration system (`00-inventories/repository_inventory.md`; `00-inventories/model_inventory.md`, header). Even the one migrated table has drifted: 11 of the ~20 columns `common/models/User.php` actually reads/writes (`user_group`, `user_type`, `phone_no`, `dob`, `last_login_ip`, `last_logout`, `login_zone`, `os`, `created_dt`, `updated_dt`, `birth_registration_no`) are absent from both migration files (`00-inventories/model_inventory.md` §23).

**This doc set has already done the reconstruction work.** `05-workflows/database_ui_mapping.md` is the closest thing this codebase has to a schema spec: every `rules()` array for `Sailors`, `DeSailors`, `User`, `SailorBatchs`, `SailorBatchConfiguration(+ExamDate)`, `SailorCenters`/`SailorCentDistMapping`, `Eligibility`, `CanEligibilityCheckInfo`, and `Districts`/`Unions`/`Upozilas` is quoted directly from source and cross-referenced against the exact view field (`ModelName[attribute]`) that populates it, with every controller-side field-remapping/overwrite call-out flagged inline (e.g. the TeleTalk-overwrite pattern in `05-workflows/database_ui_mapping.md` §1b/§2b, or the field-name-mismatch found on `resendVerificationEmail.php`, §3c). `00-inventories/model_inventory.md` is the companion doc — every one of the 47 model files was opened and read in full, with `rules()`, `attributeLabels()`, and relation methods quoted verbatim, not guessed.

**The caveat that both docs state up front, and that a rebuild must not lose sight of:** Yii `rules()` validation is application-level and does not guarantee a corresponding DB-level constraint exists, or vice versa. `['username', 'unique']` in a model's `rules()` tells you the app *tries* to enforce uniqueness; it does not tell you whether the live database column actually has a unique index. Column types, defaults, indexes, foreign keys, and charset must still be reverse-engineered from a live database dump — the reconstructed source of truth in this doc set is a floor, not a substitute for pulling the actual production `SHOW CREATE TABLE` output before writing a rebuild's migration set. `05-workflows/database_ui_mapping.md`'s own framing states this explicitly: "every field in every table below should be read as 'NOT IN MIGRATIONS' by default... Anyone rebuilding schema from this repo alone must treat every `rules()` block below as the closest thing to a spec" (not the spec itself).

**Practical consequence for a rebuild:** before writing a single migration file for the new stack, get a live schema dump (or at minimum a `SHOW CREATE TABLE` for every table named in `05-workflows/database_ui_mapping.md`/`00-inventories/model_inventory.md`) from whoever operates the current production database. Cross-reference that dump against the reconstructed `rules()` tables in this doc set to catch drift in both directions — columns the live DB has that no model rule ever validates (dead/legacy columns, safe to drop) and columns a model validates that the live DB might not actually constrain the way the `rules()` imply (e.g. `unique` rules with no matching DB index, `SailorBatchs::secrate_key`'s misspelling propagated into the column name itself per `05-workflows/database_ui_mapping.md` §4).

## 5. Security findings

Ranked by severity, consolidated from every deep-dive and inventory that surfaced a finding. Findings that touch **live payment infrastructure or plaintext-credential exposure** are ranked above findings that are merely missing-access-control-on-low-traffic-screens.

### Critical — live money movement / live credentials

1. **Hardcoded live SSLCommerz merchant credentials, committed to source control, plus TLS verification disabled on every outbound call to the payment gateway.** `common/models/payment/SSLPayment.php:16-28` — both sandbox *and* **production/live** `store_id`/`store_passwd` are plaintext class constants (`LIVE_STORE_ID = 'joinnavynavymilbd0live'`, `LIVE_PASSWORD = '67D29D06BA5D147902'`), permanently in git history. `CURLOPT_SSL_VERIFYPEER`/`VERIFYHOST` are both set `false` on **every** outbound curl call in `requestInit()` (payment initiation) and `allRequestListByTranIds()` (transaction reconciliation/validation) — this is the transport for live merchant credentials and for the response that tells the app a transaction is genuinely paid. (`00-inventories/model_inventory.md` §24; `00-inventories/service_inventory.md` §2; `04-deep-dives/deepdive_frontend_payment_verify_download.md` §2.1-2.2.)
2. **`OnlinePaymentController::actionSslSuccess()` logs a user in and marks a candidate's application paid based entirely on an unauthenticated `$_REQUEST` payload**, with no signature/HMAC verification beyond a `status == 'VALID'` string check. The gateway echoes back `value_b = "r_{sailor_id}#u_{user_id}"` verbatim; the controller splits it and calls `Yii::$app->user->login(User::findOne(['id' => $user_id]))` directly — "knowing (or guessing) a `row_id#user_id` pair and hitting `/online-payment/ssl-success?status=VALID&value_b=r_123%23u_456&...` with plausible extra fields is enough to get session-authenticated as user 456 and flip candidate 123's row to `payment_status = PAID`." (`04-deep-dives/deepdive_frontend_payment_verify_download.md` §1.3, §6 finding #2.)
3. **`refund_phone` and the final `complete-application` submit both bypass model validation entirely via `save(false)`.** `SailorCandidateController::actionRefundPhone()` reads raw POST directly (no `load()`/`validate()`), applies only a hand-rolled regex, and saves with validation skipped. `actionCompleteApplication()` — the action that commits the final roll number/exam date — never calls `load()` at all; it derives every field server-side and saves with `save(false)`, bypassing `rules()` entirely for the single most consequential write in the whole application. (`05-workflows/database_ui_mapping.md` §1c, §1d, cross-cutting finding #2.)

### High — PII exposure / bulk export / broad unauthorized reach

4. **The hardcoded-hidden-field bug silently discards eligibility-computed naval-officer/Ansar-VDP/small-ethnic-group status on every single personal-info submit.** Both `Sailors[is_child_of_naval_officer]`/`Sailors[is_anser_vdp]`/`Sailors[is_khudro_jati_gosti]` (and the `DeSailors` equivalents) are rendered as `hiddenInput` fields **hardcoded to value `2` ("No")**. (`04-deep-dives/deepdive_admin_reports.md` §3, §5, §10 finding #7.)
7. **`download-form` and `verify-candidate` — on both the Sailor and DE-Sailor tracks — perform no ownership check at all**, resolving the target candidate purely from a decrypted, reversible-cipher slug. ## 6. Business-logic complexity hotspots that need careful behavioral parity

These are the places where a rebuild is most likely to silently break real business behavior if it re-implements "what the screen looks like it does" instead of "what the code actually does." Each of these has its own detailed section in a deep-dive; treat that section as the spec, not this summary.

### The roll-number/exam-date allocation algorithm

`SailorCandidateController::actionCompleteApplication()` / `DeSailorController::actionCompleteApplication()` — the single most complex block of logic in either controller (~240 lines each), run **synchronously inline on the final POST**, with no queue/job layer to decouple it (`04-deep-dives/deepdive_frontend_application_wizard.md` §7). The algorithm, step by step:

1. Idempotency guard — re-POSTing after a roll is already assigned just advances `phase` and redirects, doesn't re-allocate.
2. **Allocation only runs at all if `batch_setting_info['roll_from'] == Constants::ROLL_FROM_BATCH`** — the only implemented branch; any batch configured with a different `roll_from` value silently does nothing on submit (no error, empty response body).
3. Resolve the base roll number via `nextRollByBatchId()` — **the two tracks' implementations return different shapes**: `Sailors::nextRollByBatchId()` returns an array keyed `['roll_no']`; `DeSailors::nextRollByBatchId()` returns a plain scalar. Callers correctly match each model's own shape, so it isn't a live bug, but it is a landmine for anyone porting the logic to a shared function.
4. **Sailor-only**: a manual `next_start_roll`/`next_start_roll_after` roll-jump override — if the computed roll exactly equals `next_start_roll_after + 1`, it is force-reset to `next_start_roll`, a manual "restart the sequence" admin knob with no equivalent on the DE-Sailor track at all.
5. Multi-config resolution with load-balancing: when more than one `SailorBatchConfiguration` row matches the candidate's batch/center/gender/designation/district, configs sharing a `roll_swap_in_group == YES` flag form a candidate pool; any config whose `group_no_of_candidate` cap is already met is deactivated in place (`status = NO`, saved immediately); the least-filled remaining config is chosen.
6. Exam-date sub-allocation: assigns the candidate to the exam date **following** the most recently used date for that center/gender/designation combo — a circular round-robin walk that wraps back to the first date when the last one was final.
7. Per-date max-candidate enforcement (only if `check_max_candidate == YES`): counts already-assigned candidates for the selected date; once at/over cap, walks forward to the next date under capacity, again circularly, marking over-limit dates as it passes.
8. **No transaction or locking wraps steps 5-7's read-then-write-then-write sequence in either controller** — under concurrent submissions near a capacity boundary, this is a structural check-then-act race: two candidates could both read "count = cap-1" and both be assigned before either write lands. Not independently exercised against production traffic; flagged as a code-reading observation both controllers share identically. (`05-workflows/workflow_analysis.md` §6, "Business rules / edge cases worth flagging".)
9. On success: two **independent** logging mechanisms fire — an R2-hosted per-batch NDJSON audit log (`upsertCandidateLog()`, decrypted-PII snapshot) and a **second**, separate local-disk debug dump (`Sailors::generateLog()`, writes to `@rootDirFilUpload/dummy/{batch_id}.txt`) — the latter reads as leftover development instrumentation, not an intentional second audit trail, but both fire on every successful roll assignment and a rebuild needs to decide whether either is load-bearing for any downstream consumer before dropping it.

A rebuild that treats "assign a roll number" as a simple auto-increment will silently break: the manual roll-jump override, the round-robin exam-date wraparound, the fail-closed "0 means uncapped is wrong, 0 means bail" semantics on `max_candidate_this_date`, and the load-balancing tie-break across parallel exam groups. **Write characterization tests against the current live behavior before refactoring any of this away** — there is zero automated test coverage for it today (`00-inventories/repository_inventory.md` "Priority cleanup list" item 7).

### The eligibility-matching engine

`CheckEligibilityController::actionEligibleDepartment()` is a real multi-stage rules engine, not a flag check (`04-deep-dives/deepdive_frontend_eligibility_wizard.md` §4.3, `05-workflows/workflow_analysis.md` §1 "Business rules"):

1. Age window computed per active batch's `circular_date` (falls back to today if no batch is open), with a **conditional branch for Departmental candidates** comparing against `dept_can_max_age` instead of `max_age` — currently dead in practice for wizard-originated rows (the public UI only ever creates `candidate_type = GENERAL` rows, per §3 below) but live for any row created another way.
2. Exact-match/REGEXP filtering against `Eligibility` config rows by gender, marital status, JSC result, and a gender-split height comparison — **no chest or eye-status comparison at all**, even though both are collected on the personal-details step; `Eligibility` has chest columns the query never selects, and no eye column exists at all.
3. Post-query PHP filtering with **four mutually exclusive shapes per matched `Eligibility` row**: (a) no SSC requirement at all → auto-pass ("for topass"); (b) SSC passes + designation requires trade-course-only → additionally requires trade-course-complete=Yes and subject match; (c) SSC passes + designation requires diploma-only → additionally requires Diploma-type + GPA floor + subject match; (d) SSC passes + neither trade nor diploma required → pass on SSC alone. **A designation configured with both `is_allow_trade_course = Yes` and `is_allow_diploma = Yes` simultaneously falls through unmatched** — an edge case the current code silently drops rather than explicitly handling.
4. A final district/gender cross-reference against active `SailorBatchConfiguration` rows determines which of the scoring-eligible designations are actually open for the candidate's district in a currently-running batch — a designation can pass the academic/demographic scoring and still be hidden because no batch configuration currently serves the candidate's district.

This same engine — SSC/HSC GPA floors, biology-inclusion requirements, trade-course/diploma mutual exclusivity, age windows keyed to `dept_can_max_age` vs `max_age` — is re-implemented independently (not shared) inside the post-signup application wizard's own academic-info step (`Sailors`/`DeSailors::rules()`'s custom validators), so a rebuild has **two places this business logic lives today**, not one, and needs to either genuinely unify them or explicitly decide to keep them separate and keep them in sync by hand the way the legacy app does.

### Sailor-vs-DeSailor track asymmetries

The full diff table lives in `04-deep-dives/deepdive_frontend_application_wizard.md` §8 — reproduced here because it is the single highest-value artifact for anyone porting the two wizards, since the two tracks look identical at a glance and are not:

| Aspect | Sailor | DE-Sailor |
|---|---|---|
| `AccessControl` | partial (`payment`/`academic-info` only) | **none at all** |
| Refund-phone flow (`actionRefundPhone`) | exists | **does not exist** |
| Self-service cancel (`actionCancelApplication`) | exists | **does not exist** — no in-app cancellation path for DE-Sailor candidates at all, front or back |
| TeleTalk skip option | not available | `$skipTeleTalkValidation` (default `true`) lets the candidate self-report GPA/group |
| SSC tamper cross-check | enforced | present in source but **commented out** — not enforced |
| TEC-board + Medical-designation GPA carve-out | present | absent |
| Diploma/Trade fields | absent — no such columns | present, required |
| `nextRollByBatchId()` return shape | array `['roll_no']` | scalar |
| `next_start_roll` roll-jump override | present | absent |
| `team` assignment on complete-application | present | absent |
| `actionDownloadForm` phone `+88` prefixing | present | absent |
| Payment `tran_id` format | `date('Ymdhis') . rand(111,999) . id` | `date('ymdhis') . rand(111111,999999)` — different case, no candidate-id suffix |

A rebuild that treats these two tracks as "the same form with a flag" will drop real, currently-live functional differences (cancellation being the most consequential — DE-Sailor candidates genuinely have no way to request cancellation today, front or back office).

### The TeleTalk external API dependency

Both wizards' academic-info step calls `common\static\StaticMethod::educationBoardResult()` — a **synchronous, plain-`http://`, hardcoded-API-key** call to `http://ebapi.teletalk.com.bd//v1.0/ebapi.php` (note the doubled slash, literal in source) inside the form-submit handler itself, not via a separate "Check Result" AJAX button the way the sibling officer app does it (`04-deep-dives/deepdive_frontend_application_wizard.md` §6). Its response both auto-fills SSC/HSC academic fields **and** cross-checks eligibility inline. On a lookup failure, both controllers flash an error and redirect back to the same step with **full page reload, form data lost** — a rougher UX than an inline AJAX failure would be. A rebuild needs to decide: keep this API dependency (same hardcoded key, same plain-HTTP endpoint — worth negotiating an HTTPS endpoint and env-sourced key with TeleTalk before going live), or replace it, and either way must preserve the DE-Sailor track's opt-out (`skipTeleTalkValidation`, self-reported GPA/group with the eligibility floor still enforced against unverified input) since it's a real, currently-used escape hatch, not dead code.

## 7. UI/asset-loading inconsistencies

Unlike the officer app's three-way competing-theme split, this app has a **much smaller, two-tree** asset footprint — but the inconsistencies that do exist are real and worth cataloguing before a rebuild assumes a clean slate.

### Two live CSS/JS trees, plus one narrow scaffold survivor

| Bundle | Purpose | Registered by | Live? |
|---|---|---|---|
| `frontend/assets/AppNavyAsset.php` ("NAVY" template, Bootstrap 5.0.0-beta3) | Candidate-facing public site | `frontend/views/layouts/mainNavy.php`, the app's **only** frontend layout | Yes — every public/candidate page |
| `backend/assets/AppAdminAsset.php` ("Hyper"/Coderthemes theme, ~839 KB) | Admin panel | `backend/views/layouts/admin.php`, backend's default layout | Yes — every authenticated admin page |
| `backend/assets/AppAsset.php` (unmodified Yii2 scaffold `site.css`) | — | `backend/views/layouts/blank.php`, selected **only** by `SiteController::actionLogin()` | Live, but narrowly — admin login screen only |
| `frontend/assets/AppAsset.php` (unmodified Yii2 scaffold `site.css`) | — | *nobody* | Dead |

(`00-inventories/css_inventory.md` summary table.) Net effect: **an admin logging in sees the plain Yii2-scaffold Bootstrap look on the login screen and a completely different, fully-themed "Hyper" admin dashboard one click later** — the same "different visual system on login vs. dashboard" pattern the officer app has, just with a narrower scaffold fallback instead of a full second competing theme.

### Double jQuery load, on both apps, for different reasons

- **Backend**: `backend/views/layouts/admin.php` hardcodes a raw `<script src=".../adminAsset/js/vendor.min.js">` tag (bundling jQuery 3.6.0 + Bootstrap 5.2.3 + SimpleBar) **outside** the asset-bundle system, while `AppAdminAsset::$depends` separately pulls in `yii\web\YiiAsset` (which publishes `bower-asset/jquery`) — jQuery loads twice on every single admin page. (`00-inventories/javascript_inventory.md`; `04-deep-dives/deepdive_admin_users_auth_settings.md` §0.)
- **Frontend**: `AppNavyAsset` loads `navy/js/jquery-3.6.0.min.js` directly; independently, any page using Yii2's `ActiveForm` widget (signup, login, etc.) triggers `ActiveFormAsset`'s own registration of `yii.js` + jQuery-via-`YiiAsset`, **regardless of `AppNavyAsset`'s own `$depends` array being commented out** — this is a correction the deep-dive research pass made to the blanket inventory-level claim that "the public site doesn't load `yii.js`" (`04-deep-dives/deepdive_frontend_candidate_auth.md` §3, §1.1). The practical effect: jQuery loads twice on every frontend page that uses an `ActiveForm`, mirroring the backend's double-load for an entirely different structural reason.

### Half-wired vendor plugins, disabled-in-place code

- `daterangepicker.css` — JS half registered (`AppAdminAsset::$js`), CSS half sitting in the same vendor folder never added to `$css`. Same "JS wired, CSS orphaned" pattern the officer app's inventory calls out for a different plugin.
- `nice-select.css` + `jquery.nice-select.js` — both commented out in lockstep on the frontend; a maintainer turned the whole plugin off without removing the files.
- `demo.dashboard-analytics.js` (would drive the admin dashboard's ApexCharts via the theme's own demo script) — explicitly commented out of `AppAdminAsset::$js`. The dashboard nonetheless shows two live ApexCharts — but by hand-rolling its own `new ApexCharts(...)` calls inline in `site/index.php` rather than using the theme's file, so this isn't actually a functionality gap, just a dead-reference-in-config one. One of those two charts' container `<div>` is permanently never rendered (`$chart_data['have_value']` can never become `'yes'` — its setter block is separately commented out) while the unconditional inline script that mounts a chart into it still runs on every dashboard load, targeting a `null` element. (`04-deep-dives/deepdive_admin_users_auth_settings.md` §1 "Admin Dashboard", §7 finding #21.)
- 52 theme-demo `.js` files and the `daterangepicker`/`apexcharts` vendor bundle ship on every admin page load with zero views referencing them.

### No shared component/design-system layer — de facto copy-paste patterns

There is no Blade-style `@component`/`@include` equivalent producing real reuse here (Yii2's own idiom, `Widget::widget()`, is used correctly for the two genuine reusable pieces that exist — `StepAndSupport`/`SupportNo` — but everything else is copy-pasted per view) (`00-inventories/component_inventory.md`):

- **Select2 init** (13 files), **`yii\jui\DatePicker` init** (26 files) — each file re-supplies its own `data`/`pluginOptions` inline rather than a shared config helper.
- **Admin CRUD page shell** (breadcrumb + card wrapper) — repeated inline across 46 of 72 non-layout backend views, including the same dead `href="#"` breadcrumb-link pattern the officer app's inventory flags.
- **Manual flash-message block** — the de-facto replacement for the dead `Alert` widget, repeated in 19 files.
- **Frontend wizard field wrapper** (`single_input__box` + `ActiveForm::fieldConfig`) — partially centralized (Yii2's own `fieldConfig` option means this repeats once-per-form rather than once-per-field, a real improvement over the officer app's Blade equivalent) but the `fieldConfig` block itself is retyped per file across 8 wizard views rather than shared.
- **Preloader/loading-spinner overlay** — identical markup repeated across 5 files, toggled from each view's own inline `$.ajax()` callbacks.
- **R2-storage conditional image-echo** (PDF/preview templates) — each of 10 templates repeats its own `if ($model->photo && Yii::$app->r2Storage->fileExists(...))` block rather than a shared image-render helper.

**One genuine positive, worth noting so a rebuild doesn't assume the worst:** unlike the officer app's dead DataTables-styled-but-not-wired admin tables, this app's `GridView` admin-list shell is **actually wired and functional** — real server-side filtering/sorting/pagination via `ActiveDataProvider`, and the `{delete}` `ActionColumn` link's confirm dialog genuinely fires wherever it's present (because `AppAdminAsset` correctly declares `yii\web\YiiAsset` as a dependency). The inconsistency here isn't "dead JS," it's that **Pjax partial-refresh is enabled on only 10 of 16 GridView pages** — the other 4 (`districts`, `can-designation`, `sailor-batchs`, `sailor-batch-configuration`) do a full page reload on every filter/sort/paginate despite importing `Pjax` and having it available. (`00-inventories/component_inventory.md` §6, "GridView admin-list shell".)

## 8. What a redesign/rebuild needs to account for

Gaps a UI/UX rebuild would need to deliberately fill, not silently inherit or silently drop:

1. **No formal RBAC — a rebuild needs to decide whether to build one or deliberately keep the flat two-role model.** Today, "admin" is a single flat role: every `user_type == 'admin'` identity that clears login has identical access to all 21 backend controllers, with the sole exception of one hardcoded `user->id == 1` check on a single report action (`ReportController::actionJsonForLs()`). There is no "read-only admin," "reports-only admin," or sub-role of any kind, and the `user_group` column that visually looks like it should provide one (`super_admin`/`admin`/`register`) is **never read by any authorization path anywhere in the codebase** — pure decorative metadata. If the business actually wants finer-grained admin permissions (a very plausible ask once this becomes a modern app with more admin users), that's a net-new feature, not a migration. (`01-architecture/role_permission_matrix.md` §1b, §2, §6.)
2. **No `GlobalSetting`/site-configuration screen exists at all.** Confirmed by a whole-repo grep — zero hits for any settings model/table/controller. The closest analogues are two hardcoded PHP files (`common/config/params.php`, `common/config/main.php`) that require a code deploy to change, covering things like mailer addresses, the R2 bucket's `verifySsl` flag, and a password-minimum-length param that (per finding above) isn't even enforced anywhere. If the rebuild wants an admin-editable settings screen (IP allowlists, SMS toggles, batch-independent global config), it's entirely net-new. (`04-deep-dives/deepdive_admin_users_auth_settings.md` §3.)
3. **No self-service admin "Change Password" screen exists.** The only way to change any admin's password — including one's own — is `UserController::actionUpdate`, and that form (per the security findings above) is actively broken UX: `password_hash` is `required` and unconditionally blanked before every render, so **it is impossible to save any other change to a user record without also typing a new password on every single save.** A rebuild needs a real self-service password-change flow for admins, not a port of this one. (`04-deep-dives/deepdive_admin_users_auth_settings.md` §2, §7 finding #6.)
4. **No admin audit-log screen that actually surfaces admin-account activity.** The one audit-trail screen this app has (`log-report/site-activity`) is not linked from any navigation anywhere (reachable only by a direct URL an admin already knows), and its hardcoded 13-controller dropdown **excludes `UserController` entirely** — meaning "who changed which admin's password and when," arguably the single most security-relevant question this screen could answer, cannot be answered through its own UI even though the underlying global logger records the data. It also has a confirmed slug-mismatch bug (`can-designations` vs. the real `can-designation` controller id) that makes one filter option always silently return zero results, and its field-level diff modal has its `old`/`new` labels inverted relative to its own commented-out "correct" version. A rebuild's audit-log feature needs to be built from the underlying NDJSON-writing mechanism's intent, not from this screen's broken UI. (`04-deep-dives/deepdive_admin_users_auth_settings.md` §4, §7 findings #11-15.)
5. **The candidate-facing auth surface needs a genuine forgot-password flow**, not the current on-screen-plaintext-random-password mechanism. Two independent, non-interoperating password-reset code paths exist today (one live and insecure, one dead-but-schema-compatible and closer to a sane design) — the rebuild should pick one design (ideally a real token/OTP-based flow) and delete the other rather than porting both. (§5 above, finding #8.)
6. **DE-Sailor candidates have no self-service cancellation path anywhere, front or back office.** If cancellation is a real business need (and it clearly is for the Sailor track, which has a full review chain — request flag → admin queue → reason display → mark-reviewed dropdown → status flip), the rebuild needs to either build the DE-Sailor equivalent from scratch or get an explicit product decision that DE-Sailor cancellation genuinely isn't needed. This is not a bug to silently fix by copying the Sailor-track code; it's a scoping question for whoever owns the DE-Sailor recruitment process. (§6 above, "Sailor-vs-DeSailor track asymmetries" table.)
7. **The eligibility-scoring engine and the post-signup academic-validation engine are two independently-maintained implementations of overlapping business rules.** A rebuild has a real opportunity to unify these into one rules engine invoked from both places — but doing so requires first fully enumerating where they've already drifted (e.g. the eligibility checker never compares chest/eye measurements even though it collects them; the trade-course-or-diploma-but-not-both edge case silently drops a valid designation configuration) so the unification doesn't accidentally change live behavior. (§6 above, "The eligibility-matching engine".)
8. **A rebuild's document-generation approach needs to reproduce three-way-plus branching, not simplify it away.** All PDF output (application forms, verification slips, reports) is rendered via mPDF fed hand-written HTML templates that branch on candidate type/track. The `application_form_pdf`/`application_verification_pdf` view pair exists per track (Sailor/DE-Sailor), and `application_verification_pdf.php` is currently **dead** — built and present on disk but unreachable from any live controller path, because `actionVerifyCandidate()` was changed to render an HTML preview page instead of streaming a PDF, without deleting the old PDF-generation branch. A rebuild should treat this as a design decision already made by the current app (verification = HTML page, not PDF) and simply not port the dead PDF branch, rather than assuming it needs both. (§3 above, "Unreachable code after `return`"; `04-deep-dives/deepdive_frontend_payment_verify_download.md` §4.3.)
9. **The payment-gateway callback URLs (`online-payment/ssl-{success,cancel,fail}`) and every slug-based public document/verification URL are almost certainly registered externally** (SSLCommerz merchant dashboard, printed callup-letter QR codes, bookmarked download links) and **cannot be silently renamed during a rebuild.** `StaticMethod::encryptPk()`/`decryptPk()` — the app-wide slug-obfuscation mechanism for every public candidate/application URL — is a custom digit-substitution cipher, not real cryptography, and changing or replacing it invalidates every previously-generated slug currently embedded in printed documents and bookmarks. A rebuild's URL-structure decisions need to either preserve these exact paths/slug scheme or budget for a coordinated cutover with whoever owns the SSLCommerz merchant config and any already-distributed printed materials.
10. **No automated test coverage exists anywhere to validate a rebuild against.** All three tiers (`common`, `frontend`, `backend`) have only default Yii2 scaffold Codeception tests — zero coverage for `CheckEligibilityController`, `SailorCandidateController`, `DeSailorController`, `OnlinePaymentController`, the roll-generation algorithm, the eligibility-scoring engine, or the payment-reconciliation logic — i.e., zero coverage for exactly the business logic flagged as highest-complexity in §6. Budget real time to write characterization tests against the **current, live** behavior of the roll-allocation algorithm and the eligibility scorer before refactoring either away; there is no safety net today. (`00-inventories/repository_inventory.md` "Priority cleanup list" item 7.)
11. **Accessibility and mobile-responsiveness were out of scope for this doc set's static-code pass** (unlike the officer-app reference doc, which included dedicated §6/§7 sections built from a grep-level spot-check). Before committing to visual-parity claims in a design system, a rebuild team should run an actual browser-based accessibility/responsiveness audit against the live `frontend/` and `backend/` apps rather than assuming this doc set already covers that ground — it doesn't.
